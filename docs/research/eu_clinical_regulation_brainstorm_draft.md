## 0. 今ある機械の棚卸し（この repo の実装から）

ブレインストーミングは、あるものから始める。以下は 2026-09-01 時点の実装であって、構想ではない。

| 部品 | 版 | 実際にやること | 出力 |
|---|---|---|---|
| `genomicschain_tier1` | 0.2.1 | 論文を読み、再現性の**主張**を採点する。版が固定されているか、環境が閉じているか、データに到達できるか。何も実行しない | 上限値（ceiling）としての readiness report、schema v0.2.6 |
| `genomicschain_codescan` | 0.2.0 | ワークフローの repository を読み、宣言されている software / container / data の**固定の強さ**を分類する。評価はしない、読むだけ | `env_capture_class` A/B/C と、rubric の段階別上限の提案 |
| `genomicschain_tier2` | 0.4.0 | 対象を計算バックエンドで**実際に走らせる**。論文が比較対象を宣言していれば出力を突き合わせる | 二軸判定: `execution_verdict`（走ったか）/ `comparison_verdict`（合ったか、そもそも対象がなかったか） |
| `genomicschain_core` | 0.3.0 | digest、受理ゲート、署名（`mmp` が鍵と身元を供給）、Synoptis への記録 | 署名つき追記記録。3.58.0 以降は検証鍵が呼び出し側からのみ来る |

記録には `environment_provenance` と `inputs_provenance` が入る。つまり
**「証明書が、運用者の作った環境を論文の宣言した環境であるかのように書くことはできない」**
**「入力が第三者の到達できない管理アクセス源から来たことを隠せない」**。
これは技術的細部ではなく、この製品が売っているものそのものである。

### この repo が既に見つけている、最も重要な事実

> 201 本の corpus のうち Tier-1 のゲートを通った 5 本を 2026-08-14 に調べたところ、
> **checksum を公開していた論文も、比較対象の artifact を指名していた論文も、一つもなかった。**

学術論文では、`comparison_verdict: no_target_declared` が**普通の結果**である。
比較する相手が存在しない。だから `gc_tier2_execute` は「走った」としか言えない。

**ここが事業仮説の起点になる。** 臨床試験では、比較対象が存在しないという状況が許されない。
プロトコルが解析計画を事前に定め、統計解析計画書（SAP）が凍結され、
規制当局は「同じデータから同じ結果が再び出ること」を要求する。
つまり —— 同じ機械を、**比較対象が法によって存在を強制される領域**に向ける、という話である。

学術界向けには「対象がない」という空振りを報告し続けるしかない道具が、
臨床領域では設計どおりに機能する。これは pivot ではなく、**適用領域の選び直し**である。

## 1. 仮説の骨格 — 何を売るのか

三層に分けて考える。下に行くほど技術に近く、上に行くほど金額が大きい。

```
  ┌─────────────────────────────────────────────────────────┐
  │ 層 C: 規制対応サービス（人 + 手続き）                    │  ← 単価大・非スケール
  │   監査対応、査察準備、ベンダー適格性評価、規制当局対話    │
  ├─────────────────────────────────────────────────────────┤
  │ 層 B: 検証サービス（機械 + 人の判断）                    │  ← 反復収益・中単価
  │   第三者による解析の再実行と一致確認、証明書の発行        │
  ├─────────────────────────────────────────────────────────┤
  │ 層 A: 記録基盤（機械のみ）                               │  ← 低単価・高スケール
  │   解析の来歴を署名つきで追記記録する                      │
  └─────────────────────────────────────────────────────────┘
```

層 A だけを売ると、既存の eClinical ベンダーが機能として吸収して終わる（要調査）。
層 C だけを売ると、それはコンサルティング会社であって deep-tech ではなく、
Pionierpreis の審査員には響かない（要調査）。

**仮説: 層 B が本体であり、層 A はその根拠、層 C はその入口。**
層 B —— 「第三者が実際に再実行して、一致したことを署名つきで記録する」 ——
は、人間のコンサルタントには（規模の面で）できず、
ソフトウェアベンダーには（利害相反の面で）できない位置にある。
自分で作った解析基盤の会社が、自分の解析の正しさを証明することはできない。

## 2. サービス案 — 個別に

各案は「使う部品 / 買う人 / 規制上の掛かり / 今それを誰が何でやっているか」で書く。
規制の掛かりの正確な条文と、既存代替の有無は調査待ち（★印は調査で検証すべき箇所）。

### A. パイプライン再現性証明書（Pipeline Reproducibility Attestation）

- **使う部品:** codescan + Tier-2 + core（署名記録）
- **買う人:** NGS ベースの assay を臨床試験のエンドポイントに使う BioTech、
  companion diagnostic を開発する診断薬企業、その解析を請け負う CRO / 中央検査室
- **中身:** 顧客のバイオインフォマティクス解析を、顧客とは独立した環境で再実行し、
  出力が一致したことを、環境の来歴と入力の来歴つきで署名記録する。
  一致しなかった場合も同じ強度で記録する（これが売り物である —— 不一致を隠さない道具は、
  一致の主張に価値を与える）
- **規制の掛かり ★:** IVDR の性能評価、解析的妥当性の実証。
  ICH E6(R3) の data governance / computerised systems。
  EMA の computerised systems and electronic data in clinical trials ガイドライン。
- **今の代替:** 社内 QA が手作業で検証、または CRO に検証を委託。★ 誰がいくらで売っているか要調査
- **弱点:** 「独立した第三者」を名乗るには、こちら側の環境と手続きが適格性評価に耐える必要がある。
  1〜3 人の会社にとって、これが最大の障壁（★ ベンダー適格性の実際の要求水準を調査）

### B. 監査証跡の意味づけ（Audit Trail Review の自動化）

- **使う部品:** Tier-1 の rubric 思想（主張を読んで採点する）を、監査証跡に向ける
- **買う人:** sponsor の QA 部門、CRO のデータマネジメント
- **中身:** 監査証跡は既にどのシステムにも存在する。問題は量であって不在ではない。
  「何万行のうち、査察官が問題にする行はどれか」を分類し、根拠つきで提示する。
- **規制の掛かり ★:** EMA の computerised systems ガイドラインが audit trail review を要求。
  Annex 11 改訂。
- **今の代替 ★:** Veeva / Medidata / Oracle が既に何かしら持っているはず。ここが激戦区の可能性。
- **正直な評価:** これは我々の技術的優位（署名記録・独立再実行）を使わない。
  参入しやすいが、差別化が弱い。**優先度は低い**と見る。

### C. 解析のバージョン漂流の追跡（"which pipeline produced this result"）

- **使う部品:** codescan の `env_capture_class` + core の追記記録
- **買う人:** 長期の試験を回す sponsor、規制当局から数年後に再解析を求められる立場の全員
- **中身:** 臨床試験のデータ保持義務は長い（★ CTR で 25 年という理解、要確認）。
  5 年後に「この p 値を出したパイプラインを再現せよ」と言われたとき、
  何が失われているかを**今のうちに**判定し、失われる前に固定する。
  Tier-1 が論文に対してやっている「上限の判定」を、進行中の試験に対してやる。
- **規制の掛かり ★:** データ保持義務、certified copy、archiving。
- **これは我々の Tier-1 の思想がそのまま効く場所。** 「まだ実行していないが、
  実行できるかどうかは今わかる」という判定は、進行中の試験にとって予防的価値がある。
- **有望度: 高。** 予防的であり、失敗の証明ではなく将来の失敗の回避を売る。

### D. AI を使った解析の来歴記録（AI Act / EMA reflection paper 対応）

- **使う部品:** core の署名記録 + KairosChain の L0/L1/L2 と chain 記録
- **買う人:** 創薬・臨床解析に AI/ML を入れ始めた製薬企業の規制部門
- **中身:** どのモデルの、どの版が、どのデータで、どの前処理を経て、どの出力を出したか。
  モデルの入れ替えを、入れ替えたと記録できる形で行う。
- **規制の掛かり ★:** EU AI Act の技術文書 / ログ保存 / データガバナンス要件（Art. 9–15）、
  EMA の AI reflection paper が要求する data provenance と traceability。
  ただし **製薬 R&D の AI の多くは high-risk に該当しない可能性が高い**（要調査）。
  該当しないなら、規制圧力ではなく自主的なリスク管理として売ることになり、予算が付きにくい。
- **有望度: 調査結果次第で大きく振れる。** AI Act の scoping が事業性を決める。

### E. 同意と来歴の突き合わせ（EHDS / GDPR 対応）

- **使う部品:** core の署名記録 + `inputs_provenance`
- **買う人:** 二次利用でデータを再利用したい製薬、Health Data Access Body に申請する側
- **中身:** 「この解析に使われた各サンプルは、その利用を許す同意の下にあったか」を、
  解析の実行記録と同意記録の突き合わせとして機械的に示す。
- **規制の掛かり ★:** EHDS の data permit、GDPR Art. 9、二次利用。
- **重大な懸念 ★:** 消去権（GDPR Art. 17）と追記専用記録の衝突。
  ここは既存プロジェクトが繰り返し躓いている場所。
  ハッシュのみをチェーンに載せ実体は off-chain に置く構成で足りるのか、
  監督当局がそれを認めているのか、必ず調べる。
- **有望度: 規制の追い風は最も強いが、法的な地雷も最も多い。**

### F. 査察準備の「予行演習」（Inspection Dry-Run）

- **使う部品:** 全部。層 C の入口商品
- **買う人:** 初めて査察を受ける小規模 BioTech
- **中身:** 査察官が要求するであろう証拠を、実際に出せるかどうか一通り試す。
  出せない箇所を一覧にして返す。人が主で、機械が従。
- **これは技術商品ではないが、**顧客に入り、痛みの実物を見て、
  層 A/B の商品を売る足がかりになる。**最初の 3 社はこれで取る、という位置づけ。**

## 3. 自分たちの不利を先に書いておく

ブレインストーミングで最も危険なのは、都合の良い案だけが残ることなので、
不利な条件を先に固定しておく。

| 不利 | 中身 | 効く緩和策（仮） |
|---|---|---|
| スイスは EU 域外 | EU の規制サービスをスイスの会社が売る構図。データ移転、代理人 ★ | スイスは製薬本社の集積地でもある。買い手が近い |
| 会社が小さい | GxP 領域のベンダー適格性評価は、1〜3 人の会社に厳しい ★ | 大学（UZH / FGCZ）の後ろ盾、層 C から入る |
| ブロックチェーンという語の毀損 | 医療ブロックチェーンには墓場がある ★ | 語を出さずに機能で売る。「署名つき追記記録」で足りる |
| 販売サイクルが長い | 製薬への販売は 12〜24 か月と言われる ★ | 最初の顧客は CRO か中央検査室か、大学病院の CTU の可能性 |
| 既存ベンダーが吸収しうる | 層 A は機能として飲まれる | 独立性を売る。自社解析基盤を持つ会社には原理的に出せない商品にする |

**独立性が唯一の構造的な堀である、というのが現時点の見立て。**
Veeva も Medidata も Lifebit も、自分の基盤の上の解析を自分で証明することはできる。
しかしそれは自己申告であり、査察官にとっての価値が違う。
KairosChain の INV-5 が「自己検証は独立した判断ではない」と言っているのと、
まったく同じ構造の主張である。この一致は偶然ではなく、
**同じ設計原理（判断の権限と判断の能力を分ける）を別の領域に適用しているだけ**である。

## 4. 調査で必ず答えを持ち帰るべき問い

1. 臨床試験のバイオインフォマティクス解析に、**第三者による再実行を要求する条文は存在するか。**
   存在しないなら、これは規制商品ではなく品質商品になり、予算の出所が変わる。
2. AI Act は製薬 R&D の AI を high-risk に含めるか。含めないなら D 案の前提が崩れる。
3. 消去権と追記記録の衝突に、監督当局の公式見解はあるか。
4. 医療ブロックチェーン企業は、なぜ死んだか。死因が我々にも当てはまるか。
5. Pionierpreis は、物理的な実証物のない software 会社に賞を出したことがあるか。
