## 人向けの要約

Tier 3 は、文書が言うとおりに計算が走るかを、**入力データを実際に受け取れる人**が自分の手で確かめて採点する段である（02:28）。確かめた人は attestation を付けるかを自分で決める（02:30）。GenomicsChain が保証するのは自分の手順と記録までで、顧客の計算が再現することは保証しない（09 warranty-scope）。記録に「検証済み」「再現された」とは書かない。

~~~
入口（二段。operator 確認済み: 「この読みでよい」38 の問い 6）
  (a) Tier 2 / Tier 2.5 の評価「再現計算環境構築可能だと判断できたら（推論を含めて）」（01:29）
      → 宣言を出せる。route A = Tier 1 + Tier 2 の G1–G8 / route B = Tier 2.5 の記録（09:135）
      推論が出すのは「組み方の案」まで（02:43）
  (b) ② ③ を走らせるかは、宣言した案が実際に組めたかで機械的に決まる（02:45）
  ↓
宣言   組む前に、実行者が署名して anchor に出す。route_ref を必ず載せる（§3.3）
  ↓
試行   実行者 = 入力データを受け取れる人（02:28。「身元ではない」は 02:14・02:33）
       ① 再構築  宣言した案が環境を作れたか — 判定条件は §3.1
       ② 再計算  その環境で完走したか — runs = 1 で一度、試行ごとに新しい出力の場所で
       ③ 再現    宣言した目標と一致したか、何本か（度合いは ③ だけ）
                 照合は実行側の道具が、② の出力 file を読んで行う（§3.2）
  ↓
出口   attestation するかは実行者が決める（02:30）。① = 作れない の試行も出せる
       手順は実行者の手元に残り、Tier 4 が蒸留する（01:31）
~~~

- **実行者は役で、身元ではない。** GenomicsChain が実行者になるかは未決である（§2.3、§8）。
- **一つの試行は、案を一度組み、組めたら runs = 1 で一度走らせ、その run を照合することである。** ① の判定の規則は §3.1（宣言した案のすべての段が exit 0 で終わり、案が固定した版・digest・取得元がそのとおり得られたときだけ 作れた）。出力の場所は試行ごとに新しくし、宣言が指した path だけを比べる〔査読 r2〕。`run_count` を試行の数には使わない。
- **照合目標は対象自身の宣言への参照である**〔査読 r1〕。route B では束の出力の行を宣言に並べ、anchor が `outputs_digest`（33:416–428）を数え直して Tier 2.5 の記録の値と等しいことを求める。**n は、並べた行のうち宣言した比較器が比べられる方式の行の数である**〔正誤〕（塩なしの束は sha256 の行、option 2 の束は hmac_sha256 の行。書き出し器は一つの出力に sha1 と sha256 の 2 行を書くので、sha1 の行は数え直しのために並べるが照合目標ではない。`outputs_with_checksum` の数でもない）。route A の完全性は実行者の申告で、`not_checked` に置く。許容範囲は exact で、対象が checksum を宣言することから来る（09:69、09:77）。
- **比較器は二つである。** 平文の目標に `exact_sha256` 0.2.0、option 2 の束の目標に新しい比較器（operator 承認「比較器を一つ足す」、29 の問い 4）。**新しい比較器は実行側の道具が持つ自分の表に置き、11 の REGISTRY には足さない**〔査読 r2〕。
- **道具は二つである**〔査読 r2〕。実行側（`genomicschain_tier3`）が組み、走らせ、照合し、署名する。鍵はこの道具の中だけにあり、どこにも送らない。anchor 側（新しい package `genomicschain_tier3_record` に置き、anchor でだけ登録される。anchor には tier3 を入れない〔実装〕）は宣言と attestation を受け、§4.1 の結び付きの検査、`outputs_digest` の数え直し、`route_ref` の解決、§2.5・§3.2・§3.3 の拒否と §3.4 の数えを行う〔凍結〕。
- **鍵は二種類である**〔凍結〕。署名鍵（実行者の提出鍵。attested の「同じ鍵」はこれ）と、commitment の鍵（C(f) を作る鍵、仕事に一つ）。route B の option 2 では顧客から受け取った束の鍵が後者で、`commitment.key_id` が名指す。束の鍵が無い salted の仕事では実行者が作り、平文の仕事には鍵が無い（§4.2）。
- **記録が時刻について示すのは二つだけである。** 宣言が anchor の envelope の時刻 T_d に、attestation が T_a に記録されたこと。組んだ時刻も走った時刻も記録に無い。
- **attestation は任意で、署名するのは実行者である。** attested とは同じ署名鍵の下の宣言を指す `tier3_attestation` があることで、宣言だけなら「宣言された、attestation はされていない」と読む〔査読 r1〕。**一つの宣言につき attestation は一つで、二つ目を断るのは anchor 側の道具自身の検査である（SubmitCore の idempotency key は断らない、36:63–71）**〔凍結〕。anchor へ行くのは手順記録の digest と数だけ（§6.1）。
- **option 2 の漏れは、ここでは閉じない**〔査読 r1〕。operator の決定（29 の問い 3）で、option 2 の記録を指す宣言は salted でなければ anchor が断る。記録 0.3 の提出路と、同じ束の仕事を route A と宣言する道は断れないので、本番前に閉じる穴として §8 に置き、手順書と約款で禁じる〔凍結〕。
- **言い方。** Tier 3 の記録は「その日、宣言どおりの結果になった」という日付つきの観察であって、将来の再現の約束ではない（§6.2 で 09 の二文を原文のまま引く）。

### 1.5 04 §12 が名指す漏れ

- option 2 の束は file の指紋の欄をすべて塩入りにする（04 §6.1）。今の Tier 3 の記録は出力 file ごとの平文の SHA-256 を載せる（10:104、10:127）ので、option 2 の束を今の形で記録するとそこで漏れる（04 §12）。
- 等級（`grade_inputs = immutable` など）からは、指紋が鍵を持つ人にしか確かめられないことは読めない。それは `journal_convention` から読む（04 §12）。
- **Tier 2.5 の記録には file ごとの指紋が無い。** 記録にある data の file の指紋に由来する値は `outputs_digest` だけで（04:194）、これは checksum を持つ出力の `[name, algorithm, hex]` の行を並べ替えて並べ、その JSON の SHA-256 をとったものである（33:416–428）。**行から数え直せる規則なので、行を宣言に並べれば anchor が記録の値と比べられる**（§3.2）。**行は checksum を持つ出力の方式ごとに 1 行で（33:422–426）、`outputs_with_checksum`——locator と checksum の両方を持つ出力の数（33:409）——とは一般に異なる**〔凍結〕。file ごとの指紋は顧客の束にある（09:110）。

## 3. 三項目の採点と、走らせる前の宣言

### 3.1 三項目

02 の三つを採点の単位にする。札は `gc-backing-0.1`（18:24–26）のままで、名前を変えない。

| 項目 | 何を確かめるか | 記録に残る値 |
|---|---|---|
| ① 再構築 | 宣言した案が環境を作れたか（規則は下） | 作れた／作れない、`env_digest`、`environment_provenance` |
| ② 再計算 | その環境で完走したか | `execution_verdict` |
| ③ 再現 | 宣言した照合目標と一致したか、何本か | `comparison_verdict`、比較器の id と版、試行ごとの m と n |

程度を置くのは ③ だけである。

**① の判定の規則〔査読 r2〕。作れたとは、宣言した案のすべての段が exit 0 で終わり、案が固定する版・digest・取得元のすべてが固定どおりに得られたことである**（得られた形は手順記録の項目 ②、§6.1）。それ以外はすべて作れないで、何も固定しない案も作れないである。案の digest は走る前に宣言に署名されている（§3.3）。組めた環境の digest（`env_digest`）は ① の出力として試行ごとに記録し、等しさの検査には入れない（§3.3、§4.1）。

**一つの試行は三つの段である。** ① 宣言した案を一度組む。組めたら ② `gc_tier3_execute` を `runs = 1` で一度走らせる。③ その走りが残した出力 file を実行側の道具（§3.2）が読み、宣言した n 本の目標と照合する。組めなかった試行は ① = 作れない の一行で、② ③ の欄は無い。① は `gc_tier3_execute` の外にある実行者自身の作業である（道具は解決済みの env を受け取る、12:75–79）。`run_count` は要求された dir の数で初期化されるので（13:65）、試行の数には使わない。m は試行ごとに記録する。

**試行ごとに新しい出力の場所を使う〔査読 r2〕。** 出力の列挙は workdir 全体を歩くので（15:65–69）、前の試行が残した file も、組む段で取ってきた file も出力として数えられる。実行側の道具は、走る前にその場所の一覧を取り、宣言が目標ごとに指した path（§3.3）のうち、走る前に無かったか走って変わったものだけを照合する。`runs = 1` の dir は試行ごとに別にする。

**案を変えたら新しい宣言を出す。** 前の宣言の下では、変えた案を採点しない。

`execution_verdict` は completed（13:112）・env_failed（13:84、13:87）・outputs_unusable（13:88）。`data_blocked` は enum にあるが（20:319）、それを出す経路は今の code に無い。今の道具が返すのは ② と、`expected_output` を一つ渡したときの一本の照合だけである（12:283–288、12:98–105、13:113）。① の採点と n 本の照合は実行側の道具の側にある（§3.2、§4.1）。

### 3.2 「どのくらい」 — 程度

**道具は二つで、名前はここで一度だけ決める**〔査読 r2〕（名前はこの草案が付けたもので、operator のものではない）。

- **実行側 `gc_tier3_attest`**: tier3 の `tool_classes`（28:11–14）に置く。案を組み、`gc_tier3_execute` を `runs = 1` で呼び、出力 file を読んで照合し、採点に署名する。commitment 鍵（§4.2）を持つのはこの道具だけで、鍵は外に出さない。塩入りと option 2 の宣言では `thoa` を断る（§4.3）。
- **anchor 側 `gc_tier3_record_submit`**: 新しい package `genomicschain_tier3_record` の `anchor_profile_tool_classes` に置く〔実装〕。core に置かないのは、この道具が prov の `outputs_digest` の規則（33:420）と記録の読み方（37:229–243）を使い、prov が core に依存するからである（core → prov は輪になる）。tier3 に置かないのは、anchor がこの道具のために tier3 を読み込むと、実行の道具（`gc_tier3_execute`・`gc_tier3_attest`）まで anchor で登録されるからである（実装査読 r1 の H1、operator 2026-10-21 問い 5「記録の部分を別 package に」）。二つの型の検査、言い方の読み手、schema も同じ package に置き、tier3 はそれに依存する。宣言と attestation を受け取って記録し、**行うのは §4.1 の結び付きの検査、route B の `route_ref` の解決（§3.3）、route B の `outputs_digest` の数え直し（下）、`data_class` の関門（§2.5）、`llm_extracted`・`operator_supplied` と二つ目の attestation の拒否、`attempts` の行数の検査（§3.4）である**〔凍結〕。照合も構築もしない。鍵も出力 file も受け取らない。

**比較器は二つで、どちらも実行側の道具の中の、その道具自身の比較器の表から呼ばれる**〔査読 r2〕。

- 平文の目標には `exact_sha256` 0.2.0 と同じ規則で、平文の SHA-256 どうしを比べる（11:59–61、11:63–77）。
- option 2 の束の目標には新しい比較器: 実行者が自分の出力の C(f) を束の鍵で作り、束の値と等しいかを比べる。gc-commitment-0.1（14:49–64）は変えない。operator が承認したのは「比較器を一つ足す」（29 の問い 4）で、`exact_commitment` はそこに例として挙げられた名、版 0.1.0 はこの草案が付けた番号である。
- **11 の REGISTRY には足さない〔査読 r2〕。** 足すと、比較器の id を任意の文字列で受ける道（12:142–146、13:150–158）から平文の指紋のまま呼べ、HMAC を一度も計算していない比較がその名で 0.3 に記録される。11 は変えない file に戻る（§5）。
- gc-commitment-0.1 は `genomicschain_prov`（14）にある。tier3 の依存に prov を足し、14 は変えずに呼ぶ（§9）〔実装〕。

出る値は四つの区分で、程度ではない: `match_exact` / `mismatch` / `no_target_declared` / `not_attempted`（11:30–51、11:80）。byte の比較は、中身が同じでも書庫の header に時刻が入る形を `mismatch` と読む（12:357–360）。

**許容範囲は exact である。対象が指紋を宣言するからそうなる**（09:69、09:77）。宣言の欄に書く（§3.3）。

**照合目標は対象自身の宣言への参照である**〔査読 r1〕。二つのどちらかである。

1. 論文が宣言した値（`source: paper_declared` と、確かめられる `source_citation`。25:135–150、10:174–180）。
2. route B の Tier 2.5 **束**の出力の指紋の項目。**宣言は束の出力の行——[名前、方式、値]（33:421–428）——をそのまま並べ、anchor はその並びから `outputs_digest` を数え直して Tier 2.5 の記録の値と等しいことを求める。n は、宣言した行のうち宣言した比較器が比べられる方式の行の数である**〔正誤〕（塩なしの束は sha256 の行と `exact_sha256`、option 2 の束は hmac_sha256 の行と `exact_commitment`）。ほかの方式の行（sha1 など）は `outputs_digest` を数え直すために並べるが、照合目標ではなく n に数えない。行は checksum を持つ出力ごとに、その出力が持つ方式の数だけ立つので（33:422–426）、locator と checksum の両方を持つ出力の数 `outputs_with_checksum`（33:409）とは一般に一致しない。n にこの数は使わない。値は束にあるもののまま（option 2 では束の鍵の下の commitment）で、塩入りの宣言でも入れ替えない（§4.3）。Tier 2.5 の記録そのものに file ごとの指紋は無い（09:110）。

`llm_extracted` と `operator_supplied` は拒む（25:144）。enum に 2 を表す値が無いので、宣言は参照の種類を自分の欄で明示する。

**n の完全性〔査読 r2〕。** route B は上の数え直しで機械的に決まり、n は宣言した比較器が比べられる方式の行の数である〔正誤〕。route A は決まらない——anchor は論文の正しい一覧を持たないので、対象の宣言を全部並べたかを確かめられない。route A の完全性は実行者の申告であり、`not_checked` に置く（§4.1）。確かめられない「部分集合は拒む」という規則は落とす。m と n は整数で記録し、比にしない。対象が何も宣言していなければ ③ は `no_target_declared` で、程度は無い（11:30–39）。

程度は、n 本を一つずつ宣言した比較器で比べ、一致した m 本を数えたものである。代表値（`rebuild` / `rerun` / `reproduce` の一つの値）は置かない〔査読 r1〕: k 回の試行から一番よい一つを、結果を見てから選べてしまう。採点は試行ごとの一覧そのものである（§4.1 の `attempts`）。比較器の id と版は宣言の欄であり（§3.3）、**記録 0.3 の `SIGNED_IDENTITY_FIELDS`（10:18–25）は実行の後に署名される欄で、宣言の欄ではない**〔凍結〕。

### 3.3 走らせる前の宣言

宣言は Tier 3 実行者が自分の**提出鍵**で署名して anchor に出す。**提出鍵（署名鍵）と仕事の commitment 鍵（§4.2）は別のものである**〔凍結〕。入れるものは、**§4.1 に一つだけ置く結び付きの一覧のすべて**（欄の名前はそこにあり、ここでは数え直さない）〔凍結〕と、次のものである。

- **仕事の同一性の規則 `gc-job-identity-0.3`**〔査読 r2〕: 覆うのは構築案の digest・`data`・`pipeline` の三つである。環境は組んでから digest が決まる（env は解決済みで渡る、12:75–79）ので宣言では縛らず、試行ごとの `env_digest` を ① の出力として記録する（§3.1、§4.1）。試行ごとの出力の場所も同一性に入らない: 記録する digest は宣言した正準の spec のもので、dir は走るときに差し替わる（13:201–218）。残る限界は絶対 path である（§5.1）。
- `source`、`source_citation`、`validated_by`（一覧の外の欄である）
- **目標ごとの出力の path**〔査読 r2〕（§3.1 の出力の切り分けが使う）
- 採点する項目
- 宣言の期限、試行の上限 `attempts_max`（§3.4 で anchor 側の道具が数える）、検査器の版と tree の指紋

**`route_ref` の解き方〔凍結〕。** route B の `route_ref` は Tier 2.5 の記録の proof_id の SHA-256 である（18:33–41）。提出のとき proof_id 自身を memory で渡し、anchor は registry から記録を読んで（prov の読み方は `reach.rb` 229–243 の `prov_manifest!`: `find_proof`、`revoked?`、`record_type`、`bundle_digest`。79–83 は constructor である）、その SHA-256 が `route_ref` に等しく、記録の `bundle_digest` が宣言の `bundle_digest` に等しいこと（37:238–240 と同じ）を確かめる〔正誤〕。route A の `route_ref` が何を指し、どう解くかはこの版では定めない（§8）〔正誤〕。解けない `route_ref` の宣言を断るのは route B だけである。03 の `prior_record` はこの欄に畳む。

**anchor は、route B の記録が option 2（`journal_convention` が commitment の形）である宣言を、`fingerprint_form` = salted でなければ断る**（operator 承認、2026-10-20 の問い 3）。**anchor が見るのは宣言した `fingerprint_form` の札だけで、値からは分からない**〔査読 r2〕: C(f) も SHA-256 もどちらも 64 文字の小文字 hex である。option 2 の束の仕事を route A と宣言すればこの検査は働かない（§8）。記録 0.3 の提出路には束への手がかりが無く、断れない（§4.4、§8）。

**`declaration_ref` と `route_ref` は salted でも平文のままである**。anchor はこの二つを解いて結び付きの検査と上の拒否を行うので、commitment にすると引けなくなる（§4.3）。

**記録が時刻について示すのは二つである**。宣言が anchor の envelope の時刻 T_d に、attestation が T_a に記録されたこと。どちらも `anchor_observed`（18:15–16）で、組んだ時刻も走った時刻も記録に無い（言い方は §6.2）。

**宣言と attestation の結び付きは、新しい attestation の spec の要件である**〔査読 r1〕。要件の一覧は §4.1 に一つだけ置く。記録 0.3 の検査はこれをしない（§1.2）。

### 3.4 試行の数と attestation の数

番号札（03 §4）・申告（03 §5）・締めの記録（03 §6）は落とす（§5.1）。試行の数を示すのは、attestation に並ぶ実行者自身の一覧（番号、三項目の採点、m と n、指紋。§4.1 の `attempts`）だけである。

**anchor 側の道具が数えるのは二つである**〔凍結〕。一つの `declaration_ref` につき `tier3_attestation` は一つだけ受ける: 提出のとき、その `declaration_ref` を指す attestation が既に記録されていないかを registry に当たり、あれば断る。そして `1 ≤ attempts の行数 ≤ attempts_max` を求め、空の一覧と上限を超える一覧を断る。

**途中で止まった試行**〔実装〕（operator 2026-10-21 問い 6「次の呼び出しで閉じる」）。試行の番号は試行を始めたときに使い切り、`attempts_max` に数える。途中で止まった試行は、次の `attempt` か `attest` のときに、手順記録に残った事実だけで行にする。組めたかは記録どおりで、構築が終わっていなければ 作れない。走った結果が記録されていればそれを、無ければ `env_failed` を置き、照合は `not_attempted` とする。attestation から試行は消えない。

**偽の成功を返さない**〔実装〕（operator 2026-10-21 問い 8）。anchor 側の道具は、自分が書いた記録しか数えず、提出の結果として返る proof がこの道具の書いたものでなければ、記録できなかったと答える（proof_id は名指さない）。Synoptis の汎用の道具で anchor の attester_id の下に proof を置けるかという根の問いは、すべての記録の型にかかわるので、この設計の外に置く（L2 hazard_anchor_attestation_issue_planted_proofs_20261021）。

**SubmitCore はこれを断らない**〔凍結〕。新しい二つの型は `SUBMISSION_KEYED`（19:26、19:247）に入るので `idempotency_key` は `sha256(submission_key)` になるが（36:247–249）、これは返答の欄であって拒否の仕掛けではない。同じ `submission_key` の二度目の提出は `recovery_branch` に入り、既にある記録を返す（36:63–71）。`attempts` の違う二つの attestation は `submission_key` が違うので、SubmitCore だけならどちらも記録される。拒否は上の道具自身の検査で行う。

残るのは、記録に出さずに走らせること（一覧に書かない試行）と、宣言を多数作って上限を小さく取る手である（05 C14）。この二つは §8 に置く。

|---|---|---|

## 4. attestation と記録、機密の境界

### 4.1 実行者が署名するもの

attestation は §3 の三項目の採点を実行者が自分の**署名鍵**（提出鍵）で署名した一枚の記録である〔凍結〕。署名するかは実行者が決める（02）。GenomicsChain は経路を用意するだけで、採点の中身を作らない。型は新しく `tier3_attestation`（record_version 0.1）とし、記録 0.3 の上に重ねる（0.3 は変えない、§5）。

**鍵は二種類で、呼び分ける**〔凍結〕。**署名鍵** = 実行者の提出鍵。宣言と attestation を署名するもので、「同じ鍵の下」とはこの鍵が同じことである。**commitment 鍵** = 塩入りの指紋 C(f) を作る鍵で、一つの仕事に一つ（§4.2）。平文の仕事には commitment 鍵が無い。

**attested とは、同じ署名鍵の下の宣言を指す `tier3_attestation` があることである**〔査読 r1〕〔凍結〕。宣言だけなら「宣言された、attestation はされていない」と読む。宣言を指さない署名済みの 0.3 の記録は attestation ではない。attestation しないという決定を載せる欄は置かない。

| 署名される欄 | 中身 |
|---|---|
| 結び付きの一覧の欄 | 下の一覧のすべて。宣言のものと等しい〔凍結〕 |
| `declaration_ref` | 宣言の digest と anchor の時刻 T_d（§3.3）。一つの宣言に attestation は一つで、**二つ目を断るのは anchor 側の道具自身の検査である**〔凍結〕（§3.4） |
| `attempts` | 試行ごとの行（番号、①②③、`backend_id`、`env_digest`、指紋、m と n）。① が「作れない」の行には ②③ が無い。行数は 1 以上 `attempts_max` 以下（§3.4） |
| `environment_provenance` | 12:30 の enum。案に推論由来が一つでもあれば `authored_by_operator` |
| `result_commitment` | §4.3 の規則による |
| `process_record_digest` | 手順記録の manifest の digest（§6） |
| `not_checked` | 申告どおりに走ったこと、入力が本物のデータであること、記録の外の実行、機械、**route A の照合目標が対象の宣言の全部であること**〔査読 r2〕 |

**結び付きの一覧は、ここに一度だけ置く**〔査読 r2〕。新しい spec が求めるのは、attestation の署名鍵が宣言の署名鍵と同じであることと、次の欄が宣言のものと等しいことである。

~~~
subject_ref / 仕事の同一性（rule と digest）/ inputs_commitment / 照合目標の参照と種類 /
比較器の id と版 / 許容範囲 / 構築案の digest / route_ref / fingerprint_form / data_class /
commitment（rule と key_id）— ただし fingerprint_form = salted のときだけ〔凍結〕
~~~

**この一覧の欄は宣言でも attestation でも必須である。`commitment` だけは条件つきで、`fingerprint_form` = salted のときに必須の結び付きの欄であり、平文の仕事の宣言と attestation は `commitment` の欄を持たない**〔凍結〕。試行ごとの `env_digest` と `backend_id` はこの一覧に入らない——組んでから決まる ① の出力である（§3.1）。**落とせるのはこの一覧の外の欄だけである**〔凍結〕（§4.3）。§3.3 と §9 はこの一覧を参照する。記録 0.3 の `assert_submitted_matches_signed!` はこれをしない（§1.2）。

**札の言い方〔凍結〕。** anchor が自分で導き直したもの——`route_ref` の解決、`outputs_digest` の数え直し、署名鍵の一致、結び付きの一覧の一致——は `procedure_checked`（prov の先例 27:52–54）。二つの時刻 T_d・T_a は `anchor_observed`（18:15–16）。それ以外、attestation が述べることは `customer_stated` で、attestation 全体は `customer_signed`（18:17–18）〔正誤〕。比較器の欄に `procedure_checked` は付けない: どの比較器が実行者の機械で走ったかを anchor は確かめられない。語彙は 18 のまま変えない。

### 4.2 鍵 — commitment 鍵は仕事に一つ

- 照合は実行者の機械の上で、実行側の道具 `gc_tier3_attest`（§3.2）が行う。署名鍵も commitment 鍵もこの道具が memory の中だけで使い、記録にも log にも書かず、どこへも送らない。
- **commitment 鍵は仕事に一つである。束の鍵が無い salted の仕事では、route を問わず実行者が作る**〔凍結〕。

| 仕事 | commitment 鍵 |
|---|---|
| route B の option 2 の束 | 顧客から受け取った**束の鍵**。`commitment.key_id`（14:66–68）がそれを名指す |
| route A で salted と宣言した仕事 | 実行者が作る 32 bytes の鍵（14:44–46） |
| route B で束が option 2 でなく、salted と宣言した仕事 | 同じく実行者が作る鍵〔凍結〕 |
| 平文（salted でない）の仕事 | 無い。`commitment` の欄を置かない（§4.1） |

- option 2 の仕事で鍵を顧客に渡すことはない。束の鍵は顧客のものである（顧客の書き出し器が束ごとに作る、04 §5・§8）。
- **凍結設計 04 は「GenomicsChain は鍵を持たない」（04:283）、「鍵を預からない」（04:118–119）と述べる。この設計はそれを保つ。** operator が GenomicsChain を Tier 3 実行者に認めるなら、この二行の見直しが要る（§2.3、§8）。
- 鍵を受け取った者はその束のすべての指紋を照らせ（04:117）、候補の少ない file は総当たりで当てられる（04:82）。鍵を持たない読者は検算できない。束をまたいだ使い回しは置かない（04 §5・§13）。

### 4.3 記録の欄 — 一つの規則

`data_class` が `human` の宣言は受けない（§2.5）。欄の決め方は `non_human` の一列だけである。

**`fingerprint_form` を `salted` と宣言したときは、どちらの記録でも、指紋と digest の欄は仕事の commitment 鍵の下の C(f)（14:49–64）である。当たるのは `attempts[]` の指紋、試行ごとの `env_digest`、`result_commitment`、`process_record_digest`、`job_identity_digest`、`inputs_commitment`、構築案の digest、route A の照合目標の値である**〔凍結〕。file でない値の digest は、その値の正準 JSON の bytes に C をかけたものである。欄ごとに平文を許す表は置かず、新しい符号化も作らない。

**平文のまま置く欄は二組である。** (1) `declaration_ref` と `route_ref`: anchor がこの二つを解けなければ §4.1 の検査も option 2 の拒否もできない。(2) route B の照合目標の参照——`bundle_digest`（route B の宣言が照合目標の参照の一部として持つ欄で、Tier 2.5 の記録の同じ名の署名欄と等しいことでどの束かを名指す。prov の先例は reach.rb 238–240。この比べは route B の `route_ref` の解決の一部である、§3.3）〔正誤〕、`outputs_digest`、束の出力の行（option 2 ではその値が既に束の鍵の下の commitment である、04 §6.1）: 仕事の鍵でもう一度包むと、anchor が `outputs_digest` を数え直せず（§3.2）、Tier 2.5 の記録との結び付きが誰にも引けなくなる。

- option 2 の束の仕事では 0.3 を提出しない（0.3 は出力 file ごとの平文 SHA-256 を載せる、§1.2）。`jobspec_json` も塩入りの仕事では送らない。
- **option 2 の束の仕事と塩入りの仕事は backend `local` でだけ走らせる。`thoa` は入力をサービスに送る（26:24、12:88）ので、記録を塩入りにしても入力そのものが外へ出る。担保は二つである**: `backend_id` を `attempts[]` の署名される欄に置き（§4.1）、実行側の道具が塩入りと option 2 の宣言で `thoa` を断る（§3.2）。
- `source_citation`・`validated_by` は自由記述。人の名前・path・試料名を書かない（05 C16）。鍵は載せない。

04 §13 の三点のうち二点はここで決まる: 一覧の file ごとの指紋を gc-commitment-0.1 にする（前置き語なしで bytes をそのまま）、宣言と attestation に `commitment` を置く（salted のときだけ、§4.1）〔凍結〕。**三点目（一覧の側に区別の前置きを付ける）は採らない**: bytes が「前置き ‖ 一覧の正準 JSON」である file は同じ値に commit するので、同じ鍵の下の取り違えを防がない（round 1 で再現）。**04 §13（04:302–303）は凍結設計が Tier 3 側に残した開いた一覧であって、凍結した仕様ではない**〔査読 r2〕。区別は欄の型（schema がどの欄を file の指紋、どの欄を一覧の指紋とするか）で引き、暗号の上の分離は §8 に置く。

### 4.4 機密の境界

- 記録に載るのは同一性と数だけである（09:110）。提出のとき anchor は材料そのものを memory で受け取る（09:146）。塩入りにしても隠れないものは 04 §3 のとおり（locator、file の名前と種類、自由記述、parameter、大きさ、数、どの段か、環境の名札、計算の種類）。
- 境界は欄で引く。符号化を走査して塩入りを求めることはしない（04:75–79）。
- **04 §12 の漏れについての operator の決定（2026-10-20、問い 3「新しい宣言で断る＋0.3 は名指し」）**〔査読 r1〕。(1) 宣言は `route_ref` を必須に持ち（§3.3）、route B の記録が option 2 であるとき、`fingerprint_form` が `salted` でなければ anchor が断る。(2) 記録 0.3 の経路には束への手がかりが無く断れない。本番の前に閉じる穴として §8 に名指しし、手順書と利用条件で禁じる。
- **anchor が確かめるのは八つである〔凍結〕**: 欄の形、route B の `route_ref` が解けること（記録の `bundle_digest` が宣言のものと等しいことを含む）、route B の `outputs_digest` の数え直し、宣言した `fingerprint_form` の札、宣言の `data_class` が `human` でないこと、`source` が `llm_extracted` でも `operator_supplied` でもないこと〔正誤〕、§4.1 の署名鍵と結び付きの一覧の一致、attestation が宣言につき一つで `attempts` の行数が範囲内であること。**指紋の値が本当に鍵入りかは分からない**（C(f) も SHA-256 もどちらも 64 文字の小文字 hex である）**し、申告が本当かも確かめない**〔査読 r2〕。option 2 の束の仕事を route A と宣言すればこの検査は働かない。§8 に置く。
- 人のデータの関門も新しい宣言にしか及ばない（§2.5）。
