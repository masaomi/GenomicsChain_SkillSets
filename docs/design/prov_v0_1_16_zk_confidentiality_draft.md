## 人向けの要約

ZK 証明（計算が正しく行われたことを、データを渡さずに示す証明書）は、今でも Tier 2.5 に任意で付けられる（option 1、v0.1.12 から）。
ただ、今の証明は秘密を守らない。証明の表書き（証明の公開部分、journal）には、その段の出力がそのまま入っている。入力の指紋も
塩なしの SHA-256 なので、候補の file を持つ人は「この file か」を確かめられる。

v0.1.16 は option 2 を足す。option 2 の束では、**file の指紋の欄（`checksums[]` と `sha1_checksum`）をすべて**、顧客だけが持つ鍵を混ぜた指紋（塩入りの指紋）にする。
表書きにも塩入りの指紋だけを書く。狙いは、証明と記録と束を渡しても、鍵を持たない人には指紋から中身を推せず、候補の file と照らし
合わせることもできないようにすること。ただし、これを主張するのは試験（§10）が通ってからにする。〔査読 r1〕

```
Tier 2.5 の記録（いつも）
  └─ option 1  ZK 証明を付ける             表書き gc-zk-journal-0.1 = (入力の SHA-256, 出力そのもの)
       │                                    鍵は要らない。照合は今のまま（版の番号は上がる、§4 S3）。証明を持つ人は出力を読める
       └─ option 2  中身の秘密も守る       表書き gc-zk-journal-0.2 = (型の印, 鍵の名札, 入力の塩入り指紋, 出力の塩入り指紋)
                                            束の指紋はすべて塩入り。証明は 1 枚にまとめた型（succinct）だけ。鍵は anchor に渡らない
```

分け方の要点は三つ。① option 2 は option 1 の一つ目と二つ目の照合（証明そのものの確かめ）を同じに使い、束との結び付けの照合だけを
塩入りの値で置き換える。option 1 は鍵を一切使わない。② 一つの束はどちらか一方の型だけを使い、二つの型の表書きは互いの型として
読めない。③ anchor は設定で option 2 を開け閉めできる。開け閉めは anchor ごとで、顧客ごとではない。〔査読 r1〕

守らないものもある。file の住所（locator）と名前、file の種類、束の自由記述や parameter の欄、大きさ、どの検査プログラムが走ったか、数、
どの段か。環境の名札（container image の digest、workflow の git commit とその置き場所の指紋）も塩なしのまま残る〔反証 r1〕。鍵を渡された人には、その束のすべての指紋が照らせる。公開の file（参照ゲノムなど）も option 2 の束では鍵なしでは照らせなく
なる。〔査読 r1〕

計算の増え方は小さい見込みである（推定。§10 の T5 で実測する）。入力の指紋は、今の検査プログラムが既に計算している SHA-256 を
鍵入りの計算に置き換えるだけで、増えるのは SHA-256 の 3 block 程度。出力の指紋は新しく計算するので、出力の大きさに比例して増える
（S1 の例の出力は 32 bytes）。増えるのは主に手間のほうで、検査プログラムの作り直し、鍵の管理、鍵を持つ監査人が中身を照らすための
道具がそれにあたる。

論文 v1.0 の「秘密は主張も検証もしていない」は、試験が通るまで正しいので変えない。

## 3. 守る相手、守るもの、守らないもの

- **守る相手:** 証明・記録・束を受け取る第三者（論文の補足資料や公開の置き場所に置かれた場合を含む）。それに GenomicsChain の anchor。
  anchor は option 2 では、どの file の塩なしの指紋も、覆われた段の出力も受け取らない（option 1 では、証明の bytes の中の表書きに出力が
  入っている）。
- **守るもの:** 束のすべての file の、候補と照らせる指紋。証明が覆う段の出力の中身。
- **守らないもの〔査読 r1〕:**
  - 束の指紋以外の欄: locator と file の名前、file の種類（mediatype）、自由記述（段の説明、`error_domain` など）、parameter の欄、大きさ。
    これらに中身や指紋を書くかは顧客の責任で、anchor は調べない（locator が中身の指紋を含む形——`…/sha256/<指紋>` のような住所——も
    同じ）。
  - 計算の種類（L4）、数（L5）、どの段か。
  - 環境と workflow の名札: locator の中の container image の digest（`image@sha256:…`。書き出し器自身が書く、`nextflow_run.rb` 551–561 行）、workflow の git commit（記録に署名欄 `workflow_commit` として載る）、置き場所の URL の指紋（`workflow_repository_sha256`）。どれも環境を名指すもので、data の file の指紋ではない〔反証 r1〕。
  - 正直でない検査プログラム。照合が確かめるのは表書きの値と束の値が等しいことだけで、値が本当に鍵入りの指紋かは、image ID が名指す
    検査プログラムがそう計算する場合に限って成り立つ（§6.3）。
  - 鍵を持つ人。鍵を渡された人（監査人、Tier 3 の実行者）は、その束のすべての指紋を照らせ、中身の候補が少ない file は総当たりで当てられる。
  - 証明を作る者。証明は顧客が自分の機械で作る（既定。§8）ので、証明を作る者は顧客自身である。

## 5. 塩入りの指紋の規則 — `gc-commitment-0.1`（Tier 3 と共有）

```
鍵        32 bytes ちょうど。暗号用の乱数で作る。anchor には渡さない
指紋      C(f)   = HMAC-SHA256(鍵, f の bytes)            64 hex、小文字
鍵の名札  key_id = SHA-256("gc-commitment-0.1/key-id" ‖ 鍵)  64 hex、小文字
```

- **一つの束に鍵は一つ。** 書き出し器が束ごとに新しく作る。別の束で鍵を使い回す指定は置かない（使い回しを支える欄が記録に無く、
  key_id が同じことは、預けられた宣言を写した第三者でも作れる。§13）〔査読 r1: r0 の「明示の指定で使い回す」を削った〕。
- **鍵の長さは、読むたびに 32 bytes であることを確かめる**（書き出し器、検査プログラム、照らす道具）。HMAC は短い鍵を 0 で埋めるので、
  長さの違う鍵が同じ鍵として働くのを防ぐ〔査読 r1〕。隠す性質は、鍵が一様な乱数であることを前提にする。
- **鍵の名札は、鍵を名指す。** 中身を照らす人は、受け取った鍵が束の鍵であることを確かめられる。anchor が確かめるのは、表書きが申告する
  名札と束の名札が等しいことだけで、検査プログラムが本当にその鍵で指紋を作ったかは確かめられない（§6.3）〔査読 r1: r0 は「anchor は
  すべての証明が同じ鍵を使ったことを確かめられる」と書いていた〕。
- **束縛。** 作った後で中身を差し替えられないこと（束縛）は、SHA-256 の衝突困難性による: 同じ鍵で別の中身が同じ C になるなら、HMAC の
  内側か外側の SHA-256 に衝突がある。〔反証 r0〕
- **隠す性質。** 鍵を持たない人には、C(f) から f を推すことも、候補の file と照らすこともできない。これは計算量の上での性質で、
  HMAC-SHA256 が擬似乱数関数（鍵を知らない者には乱数と区別できない関数）であるという標準の仮定による〔反証 r0〕。隠さないもの: 同じ
  鍵の下では同じ file が同じ指紋になる（束の中で等しいことは見える）。key_id を公開することは HMAC の標準の証明の外にあり、SHA-256 を
  理想的な hash と見なす前提で問題ない。鍵は検査プログラムの非公開の入力なので、zkVM が非公開の入力を漏らすなら鍵も漏れる（L7）〔査読 r1〕。
- **鍵を渡すと、** 受け取った人はその束のすべての指紋を照らせる（覆われた file に限らない）〔査読 r1〕。
- **鍵を失うと、** 誰も照らせなくなる。記録はそのまま有効で、「提出の日に anchor が照合した」ことは残る。GenomicsChain は鍵を
  預からない（10-14 の決定「データを預かるサービスはしない」）。控えの取り方は顧客の手順書に書く。
- **Tier 3 段階 0 の `salted` はこの規則に合わせる。** 段階 0 の草案の `salted` は、一覧の指紋（`[{path, sha256}]` の正準 JSON）と
  照合目標に HMAC を一つずつかけるもので（草案 §3: 「顧客だけが持つ秘密の値を鍵にした HMAC-SHA256」、§5: 「salted なら同じ秘密の値の
  HMAC」）、一覧の中の file ごとの指紋は平文の SHA-256 のまま、鍵の長さも名札も決めていない〔反証 r0〕。この草案は鍵の形（32 bytes）、
  名札、file ごとの指紋の規則を決める。段階 0 の草案をこれに合わせて直すのは Tier 3 の設計の仕事で、この版ではしない（§13）。

## 6. 束の書き方と anchor の照合

### 6.1 束

- **option 2 の束の file の指紋の欄には、塩なしの指紋を一つも置かない**〔査読 r1、operator 承認。反証 r1 で範囲を明記: 指紋の欄の規則で、§3 の環境の名札は対象外〕。0.2 の証明を宣言する束では、`checksums[]` の項目は
  `uri` と `hmac_sha256` の二つの欄だけを持ち（許可の一覧。ほかの欄——`sha256`、`md5` など——があれば拒否）、BCO 標準の `sha1_checksum`
  もどこにも無い〔凍結: r1 は禁止の一覧だった〕。あれば拒否
  （理由 `plain_fingerprint_in_option2_bundle`）。r0 の「覆われた file の locator だけ」を調べる規則では、同じ中身が別の locator で塩なしの
  指紋を持つ形（L3 の公開用の写し）を見逃した。書き出し器 0.4.0 は option 2 の束でこれらを書かない。代わりに失うもの: 公開の file
  （参照ゲノムなど）も、option 2 の束では鍵なしでは照らせない。道具・script・engine の指紋も同じ欄にある（`bco.rb` 306–321・358–385・
  645–651 行）ので塩入りになり、software・workflow・runtime の固定も鍵を持つ人しか確かめられない〔凍結〕。この規則が確かめるのは欄の形で、
  値が本当に鍵入りの指紋かは確かめない（§7）。
- 拡張に一度だけ `commitment = {rule: "gc-commitment-0.1", key_id: <64 hex>}` を置く。拡張の block が複数あって `commitment` が食い違えば、
  どちらも採らない（`producer`・`platform` と同じ規則）。そのとき 0.2 の証明は ⑤ で落ちる（理由 `commitment_declared_twice`）〔査読 r1〕。
- `checksums[]` の項目は `sha256` か `hmac_sha256` の、どちらか一方だけを持つ。塩入りの指紋と `commitment` は option 2 の束でだけ書ける。
  0.2 の証明を宣言しない束にあれば拒否（理由 `commitment_outside_option2`。S3 (vii)）。
- **等級。** アダプタは `hmac_sha256` を、`sha256` と同じく中身を固定する指紋として読む。述語（等級の規則）は変えない（述語は、アダプタが
  作る指紋の有無で等級を出す。`predicate.rb` 222・281・301・338・403・409 行）。中身を固定すると言えるのは、作った後で中身を差し替えるには
  SHA-256 の衝突が要る（§5）からだ。ただしそれを確かめられるのは鍵を持つ人だけで、検査プログラムが §6.2 のとおりに作った場合に限る。
  Tier 3 の route B が読む `grade_inputs = immutable` も、option 2 の束ではこの意味になる〔査読 r1〕。読み方が変わるのでアダプタの版を
  上げる（§9。option 1 への影響は S3）。
- **記録の `outputs_digest`。** 行（出力の名前・方式・指紋）は、option 2 の束ではすべて方式 `hmac_sha256` とその値になる（述語は指紋の欄の
  名前で行を作る、`predicate.rb` 423–425 行）。行の規則 `gc-outputs-rows-0.1` は変えず、方式の欄に新しい値が入るだけ〔反証 r0〕。

### 6.2 表書き `gc-zk-journal-0.2`

- **形〔査読 r1、operator 承認〕。** risc0 serde の `(u32, [u8; 32], [u8; 32], [u8; 32])` = (型の印, key_id, C(段の入力), C(段の出力))。
  型の印は `0x475A4B32`（10 進で 1196051250。ASCII の "GZK2"）〔凍結: r1 は値を実装に任せていた〕。長さは 97 語 = 388 bytes ちょうど（risc0 serde は 1 byte を u32 の 1 語と
  して書き、固定長の配列に長さの語を付けない。risc0-zkvm 3.0.6 の `serde/serializer.rs`。0.1 の S1 の証明の表書きは 260 bytes）。
- **型を取り違えない。** risc0 の読み取りは表書きを最後まで読んだかを確かめない（`deserializer.rs` 75–89 行）ので、r0 の形では二つの型が
  互いの型として読めた（模擬: 本物の 0.2 の約 25% が 0.1 として、7〜30 試料の補正係数の 0.1 はすべて 0.2 として読める）〔査読 r1〕。
  `gc_zk_verify` は 0.2 では型の印と長さ 388 bytes の両方を求める。0.1 の表書きの最初の語は 1 byte（255 以下）なので型の印に一致しない。
  0.2 の表書きを 0.1 として読むと、最初の語が 255 を超えるので 1 byte として読めない（この二つは T4 で確かめる）。
- **succinct だけ〔査読 r1、operator 承認〕。** 0.2 の証明は 1 枚にまとめた札（succinct receipt）に限る。`gc_zk_verify` は 0.2 で、証明の
  中身の型が succinct であるものだけを受ける（許可の一覧）。区切りの札（composite、L6）も、Groth16 に変換した札も、試験用の偽の札も断る〔凍結〕。
- **検査プログラムの約束。** 鍵・入力・出力を非公開の入力として読み、鍵が 32 bytes であることを確かめ、key_id と二つの指紋をその一つの
  鍵から自分で計算し、検査に通ったら四つを書く。検査の中身は 0.1 の検査プログラムと同じでよい。この約束を守るかは image ID が名指す
  program の性質で、anchor は確かめない（`not_checked: zk_guest_program_semantics`）〔査読 r1〕。

### 6.3 anchor の照合（0.2）

```
① bytes の sha256 = 宣言の sha256                         （0.1 と同じ）
② Receipt::verify(image_id) が通り、succinct である        （0.1 と同じ + succinct）
③ 表書きの C(入力) = 束が input_uri に書いた hmac_sha256
④ 表書きの C(出力) = 束が output_uri に書いた hmac_sha256
⑤ 表書きの key_id  = 束の commitment.key_id
   （型の印と長さ 388 bytes は、表書きを読む前提として確かめる）
```

- **照合が示すこと、示さないこと〔査読 r1〕。** ③④⑤ が示すのは、検証できた表書きの値と、提出者の束の値が等しいことだけである。
  0.1 の ④ は anchor が表書きの出力そのものから計算した指紋を比べたが、0.2 の ③④⑤ は検査プログラムが書いた値を比べる。値が本当に
  その鍵で作った指紋かは、検査プログラムが §6.2 の約束を守る場合に限って成り立つ。
- **証明の写し〔査読 r1〕。** option 2 では表書きの値が公開されうるので、誰でも同じ値を書いた別の束を作り、同じ証明で記録を得られる。
  option 1 でも同じことができる（表書きの指紋が読めるので）。記録が示すのは「提出者の束が、検証できた表書きと等しい値を持つ」ことで、
  証明を誰が作ったかではない。誰が出したかは提出の鍵が示す。より強い結び付けは §13。
- `gc_zk_verify` は 0.2 なら四つの値の hex を返す。値は塩入りか定数なので、返しても中身は明かさない。ただし記録にも log にも書かない
  （§6 の不変条件。記録は同一性と数だけ）。
- **C4 — anchor は、どの file の塩なしの指紋も、覆われた段の出力も受け取らない。** 0.2 の照合に使う材料は、証明（表書きは型の印と塩入りの
  値だけ）と、束の塩入りの指紋だけである。束の指紋以外の欄（§3）は受け取る。

### 6.4 記録 — record_version 0.5

  第三者が「Tier 2.5 の記録の束と同じ入力を持っている」ことは、§7 の照らす道具で、記録・束・鍵の三つから確かめる〔査読 r1: r0 は
  「記録と」と書いたが、記録には file ごとの指紋が無い〕。鍵を受け取った第三者は、その束のすべての指紋を照らせる（§5）。GenomicsChain は鍵を持たない。
- Tier 3 段階 0 の `salted` は §5 の規則に合わせる（§13 の三点）。Tier 3 の出力の指紋をどう載せるか（operator の保留の案: 実行ごとの承認と
  鍵つき hash 一つ）は、Tier 3 の設計で決める。
- option 2 の秘密は Tier 2.5 までである。いまの Tier 3 の記録は出力の file ごとの塩なしの SHA-256 を載せる（`verdict_spec/tier3.rb` の
  `output_files`）ので、option 2 の束を Tier 3 で走らせて今の形で記録すると、そこで漏れる〔凍結〕。等級（`grade_inputs = immutable` など）
  からは、指紋が鍵を持つ人にしか確かめられないことは読めない。それは `journal_convention` から読む。
- Tier 4 が蒸留に使うのは、Tier 3 の実行者の手元に残る手順の記録であって、ZK 証明ではない。v0.1.16 は Tier 4 に何も足さない。

## 13. 決めていないこと

- RISC Zero の succinct receipt と、Groth16 に変換した receipt とで、zero-knowledge の扱いがどう違うか〔要確認: 現行の文書〕。違うなら、
  変換を option 2 の中の選択肢にするか。変換には計算と別の環境が要る可能性がある（未確認）。
- option 2 の外で（ZK 証明なしで）塩入りの指紋を束に書けるようにするか。この草案では option 2 の束に限った（§6.1）。
- Tier 2.5 に人のデータの関門を置くか。option 2 でも、束の指紋以外の欄（§3）は提出のとき anchor の memory に届く。Tier 2.5 の設計には今、
  人のデータの関門が無い。
- 顧客に渡す、証明を作る一般の道具（§8 の穴）。
- succinct だけを受ける規則（§6.2）は Groth16 に変換した receipt も断る。上の Groth16 の問いを決めるときに、この規則も見直す〔反証 r1〕。
- option 2 を顧客ごとに許可する仕組み（S4 は anchor ごと）〔査読 r1〕。
- 証明を提出者に結び付ける、より強い仕組み（§6.3 の写し）〔査読 r1〕。
- Tier 3 段階 0 を §5 に合わせる三点〔査読 r1〕: 一覧の中の file ごとの指紋をこの規則にする、宣言に key_id の欄を置く、file の指紋と一覧の
  指紋が同じ鍵の下で取り違えられないよう、一覧の側に区別の前置きを付ける。束をまたいだ鍵の使い回し（§5 で削った）もここで決める。
